# Higher-order callback (#217) — research state

## Purpose

Living search state for #217. Git log records WHAT was done, in
sequence. This file records WHY: what's currently believed, what's
being tested, and what to do next.

Read this file first on any new session. Update in place as findings
arrive. Append-only where noted; edit-in-place otherwise (never
delete entries — mark `[void]`).

## How to use this file

- **Claims ledger** — evolving statements about the code / design.
  Stable ids (K1, K2, ...). Update content in place when evidence
  lands; log the change.
- **Experiments** — the primary unit of work at low/medium
  confidence. Each has hypothesis, prediction, apparatus, observed
  outcome, `new options revealed`, and the commit SHA that captures
  it (engineering discipline: scientific results anchored in git).
- **Options table** — the search space. Options aren't tried
  directly; experiments try options. Tag `[science]` (needs
  validation), `[engineering]` (mechanical once shape chosen), or
  `[science→engineering]` (validate then execute).
- **Composed candidates** — templates for large experiments. Each
  is a hypothesis-driven combination of options.
- **Session log** — append-only. Each entry notes both what was
  LEARNED (science) and what was LANDED (engineering) with SHAs.

## Working with this document across sessions

**At session start:**
1. Read this file top-to-bottom. Everything needed to resume is here.
2. Check `git log --oneline` for commits since the last session-log
   entry — sync your mental model with actual code state.
3. Check test suite state matches what the session log says. If the
   suite has drifted red, that's your first task.
4. Pick the next experiment: highest information yield among those
   whose prereqs are `[high]`, respecting the iteration budget.

**During a session:**
1. State the current experiment's hypothesis and prediction BEFORE
   running it. If you can't write them clearly, the experiment is
   underspecified — refine first.
2. After running: record outcome, update affected claims IN PLACE
   (change content, keep id stable). Log the change in the session
   log.
3. **CRITICAL — extend the search space.** After every experiment,
   before moving to the next, ask: "does this evidence reveal
   options I hadn't listed?" If yes, add them to the options table.
   Common triggers:
   - An experiment surfaces a mechanism I didn't know existed →
     possibly enables a simpler option.
   - A claim voids → the options that assumed it need alternatives.
   - A partial success on one axis suggests a hybrid combining it
     with a different mechanism on another axis.
   This habit is what keeps the search space from stagnating.
   Extending the tree is NOT optional — if a session ends without
   the options table having grown or refined, log WHY in the session
   log (e.g., "experiment confirmed existing option; no new axes
   exposed").

**At session end:**
1. Everything committed: `git status` clean.
2. Session log has an entry with SHA(s) landed and one-line insight.
3. Suite state matches session log's claim (green or specific known
   failures).
4. Options table has evolved OR the session log explains why not.
5. Next action stated at end of session log entry so the next
   session knows where to pick up.

**When to compact:**
If skipping more than ~5 obsolete/tried rows to find live options,
rewrite the options table (not append). Preserve tried/obsolete
entries in a "closed set" appendix so nothing is lost, but the
working set stays scannable. Log the compaction as a session entry.

## Autonomy rules

Before escalating to the user, do all of:

1. Can the answer come from reading the code?
2. Can it come from trying + reverting?
3. Can it come from re-reading the design docs?
4. Can it come from checking existing tests for intent?

Only escalate if all four fail AND the ambiguity has material
consequences.

When escalating, state: what was verified, what was tried, what
specific choice needs input, what makes it consequential.

**Iteration budget.** 3 attempts on a branch without measurable
progress → stop, log, revisit the tree. Not before.

## Decision procedure

At each decision point, ask FIRST: what's my confidence level?

**Low confidence** (design shape unclear, hypotheses unverified):
- Unit of work = experiment (state hypothesis, predict outcome, run,
  observe, update claims).
- Scope follows experimental design: smallest apparatus that
  produces falsifiable evidence for the hypothesis. Can be a grep,
  can be a hundred-line prototype behind a git branch.
- Prioritize experiments by information yield ÷ cost. Prefer ones
  that resolve multiple open claims.
- Failure with matched prediction = success (evidence lands).
  Failure with mismatched prediction = interesting (shifts the
  search space). Ambiguous failure = experiment was underspecified,
  refine the hypothesis.

**High confidence** (shape settled, evidence pointing one way):
- Unit of work = engineering deliverable (build the direction,
  land cleanly, verify).
- Blast radius now matters — small incremental commits, each
  attributable.
- Watch for evidence the direction is wrong; be willing to demote
  confidence and switch back to experiments.

**Backtracking triggers:**
- Claim voided → scan every option whose prereqs list it; re-score.
- Experiment mismatched prediction → update affected claims, rescore.
- 3 attempts without progress on any branch → stop.
- Regression appears after a "successful" adoption → un-promote,
  re-experiment.

## Engineering discipline (applies at all confidence levels)

E-D1. Suite-green invariant. Baseline must be green before any
      experiment. Red states never persist across sessions.
E-D2. Commit per experiment. One attempt per commit. Message
      references the experiment id (e.g., "prototype for E1") so
      revert is precise and history is auditable.
E-D3. Prototype code standards. Prototypes may get promoted; write
      them at production quality even during exploration. No
      throwaway that survives.
E-D4. Session cadence. Each session lands SOMETHING committed —
      a claim update, an experiment result, a code change. No
      pure-thought sessions.
E-D5. Doc updates land alongside evidence. If an experiment shifts
      a claim, the doc update is part of the same commit as the
      experiment's evidence.
